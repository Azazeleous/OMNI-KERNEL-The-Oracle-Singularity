# Professional Landing Pages Kit v5.0.0

A source-backed AIDesigner procedure, an original static landing-page starter,
and a GitHub Pages release workflow that others can reuse. The generated
starter code is MIT licensed. AIDesigner's service and any imported assets
retain their own terms and licenses.

## What was obtained, and what was added

AIDesigner publicly documents a prompt/context → generate → refine → export
process. Its MCP documentation supports `generate_design` and `refine_design`
with `design_mode: "ultradesign"` for its higher-fidelity workflow. Brand kits
and references can guide consistency. Exported code can enter an ordinary
development process. This kit uses that public procedure; it does not claim
access to AIDesigner's private model internals.

The independent additions are a reusable brief, a restrained black-and-gold
design, local assets, artifact checks, real browser verification, pinned
GitHub Actions, and a dedicated Pages build directory. The bundled starter
was authored for this kit; it was not generated by an authenticated AIDesigner
run. See `VALIDATION.md` for the actual execution evidence.

## 1. Establish the offer

Fill `prompts/landing-brief.md` with the product, intended visitor, supportable
benefit, one primary action, and approved evidence. Use assets you own or have
permission to use. Omit invented reviews, customer logos, statistics, and prices.
Do not create a lead form without a real submission service and clear purpose.

## 2. Generate and refine in AIDesigner

Use the completed brief in the AIDesigner editor. For a connected MCP agent,
ask it to generate with `design_mode: "ultradesign"`, then refine desktop and
mobile using specific feedback. Use the actual detected repository context,
brand kit, and supplied content. Do not invent run IDs or returned HTML.

Optional official Codex setup, run only in a repository you trust:

```bash
npx -y @aidesigner/agent-skills init codex --trust-project
npx @aidesigner/agent-skills doctor codex
```

Finish the OAuth connection in the client's MCP interface. API keys and OAuth
tokens belong in the host's credential storage, never in site code, prompts,
Drive exports, commits, or browser localStorage. AIDesigner's private working
directory is excluded by this kit's `.gitignore`.

The MCP route is an optional, documented integration. Authentication and paid
generation were not executed while assembling this kit.

## 3. Adopt the export and improve the quality

Keep the approved page in `site/index.html` and local assets in `site/assets/`.
Normalize inline event handlers and scripts into `site/assets/site.js`; move
styles into `site/assets/site.css`. If using Tailwind, compile its CSS locally
before release. Preserve approved visual content, a visible keyboard focus,
one h1, semantic landmarks, browser zoom, and reduced-motion behavior.

Review the page in five passes: clarity, composition, evidence, accessibility,
and delivery. A compelling page can omit irrelevant pricing or testimonial
sections. Professional quality is a design goal; no conversion uplift is
claimed without a real measurement plan.

## 4. Run the complete local quality pass

Requirements: Python 3.11+, Node 22+, npm, and network access for first-time
dependency/browser installation. The site itself has no runtime dependencies.

From the kit directory, run this one block:

```bash
(
  set -e
  npm ci --ignore-scripts --no-audit --no-fund
  npx playwright install chromium --only-shell
  npm run build
  npm run check
  npm test
)
```

On Linux, missing browser system libraries can be installed using the official
Playwright command `npx playwright install --with-deps chromium --only-shell`.
This command is used on the GitHub-hosted runner.

The artifact checks cover required HTML metadata, landmarks, local links,
unsafe execution patterns, selected credential patterns, private addresses,
unapproved email publication, and a combined 100 KiB gzip budget. They print
finding categories and filenames, never matched credential values.

The browser pass serves the actual `dist/` page under a project subpath. It
checks four viewport widths, horizontal overflow, runtime/resource failures,
WCAG-tagged axe rules, skip-link focus, the primary CTA, native FAQ expansion,
and a real clipboard write/read. It stores reports and screenshots locally in
`.evidence/`. Those working records are excluded from the published site.

Automated checks do not replace manual content review, screen-reader testing,
or testing other browser engines. The source scanner is bounded; it is not a
complete repository-history audit or a guarantee against every secret format.

## 5. Integrate with GitHub Pages

### Standalone repository

Use the kit as the repository root. Its `.github/workflows/pages.yml` validates
pull requests and the production branch. Only the production branch can
deploy. Configure **Settings → Pages → Source → GitHub Actions** before the
first production release. Ensure the `github-pages` environment permits the
production branch. If the default branch differs from `main`, update the
workflow branch conditions.

The deployment job receives `pages: write` and `id-token: write`; the check job
has read-only source access. Actions are pinned to verified full commit SHAs.
Pull-request code cannot reach the deployment job. The artifact contains only
`dist/`, never the repository root, imported archives, private logs, or prompts.

Set the repository variable `SITE_URL` to the verified HTTPS Pages URL,
including its project subpath. Leave it unset until the destination is known.
The build then adds a canonical URL, sitemap, and robots file. It rejects URLs
containing credentials, query parameters, or fragments. Relative asset paths
also work for custom domains and GitHub project sites.

### Omni-Kernel integration

The integrated kit lives in `templates/aidesigner-pages-v5.0.0/`. The root
`landing-page-quality.yml` runs its quality checks on relevant pull requests
and production-branch changes. The root `landing-page-pages.yml` is a manual
production workflow for this dedicated landing page. It cannot publish the
surrounding runtime or source archive. Enable Pages from GitHub Actions before
running that manual workflow from `main`.

The integration adds a release procedure; a live Pages deployment is not
claimed until GitHub returns a successful deployment result. If another Pages
workflow is added later, keep one chosen deployment path and preserve its site
root rather than installing a second competing automatic publisher.

## Security and portability boundaries

The public site uses a restrictive meta CSP and no analytics, backend tokens,
personal contact data, or network-loaded assets. Authentication, paid design
generation, and private content stay outside the static artifact.

Browser-delivered HTML/CSS/JavaScript remains inspectable and copyable. Hiding
DevTools, blocking right-click, and obfuscation do not secure secrets. The CSP
`frame-ancestors` directive cannot be enforced through a meta element; proper
anti-framing requires an HTTP response header from infrastructure you control.
Do not claim `_headers` or an HTML meta tag configures that header on GitHub
Pages. Use an appropriately configured fronting service when it is required.

## Evidence-first improvement cycle

DISCOVER the offer and sources → OBSERVE the rendered page → NORMALIZE exports
into local assets → CLASSIFY findings → VERIFY checks → FINGERPRINT the built
files → LOOKUP_REMEDY in the guide → APPLY_REMEDY as a reviewable change →
REVERIFY the actual artifact. Record outcomes, not simulated production status.

## Files and reuse

The versioned installer `GAIA_LANDING_PAGES_v5.0.0.sh` downloads the exact
recorded source commit, verifies each file's SHA-256, and installs into a new
directory. It refuses to overwrite an existing destination. With Python 3.11+
available, run it from the downloaded package:

```bash
bash GAIA_LANDING_PAGES_v5.0.0.sh
```

Its default destination is `~/landing-pages-v5.0.0`; set
`GAIA_LANDING_TARGET` to choose another new directory. It runs the static build
and artifact checks and records the result. Browser QA remains the separate
Node/Playwright command above, or the integrated GitHub check.

- `site/`: editable landing page.
- `prompts/landing-brief.md`: reusable brief and refinement passes.
- `tools/`: artifact build, bounded checks, and real browser QA.
- `.github/workflows/pages.yml`: standalone Pages deployment procedure.
- `package-lock.json`: exact QA dependency resolution.
- `action-pins.json`: recorded GitHub action versions and immutable SHAs.
- `VALIDATION.md`: scope and actual verification results for this release.

The Drive package includes this guide, the full source archive, the standalone
workflow, and a versioned one-command installer. Sharing a Drive folder still
depends on its existing permissions; no email invitations are sent by this kit.
